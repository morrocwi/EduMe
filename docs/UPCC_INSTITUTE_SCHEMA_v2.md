# Independent Institute Curriculum Design Paper Schema
## UPCC-Core Edition — เอกสารออกแบบหลักสูตรสำหรับสถาบันอิสระ
### Problem-Centered · Capability-Based · Tool-Replaceable · Modality-Aware · AI-Ready

**Version:** 2.0  
**Status:** Guideline / production schema — ไม่ใช่แบบฟอร์มขออนุมัติจากหน่วยงานรัฐ  
**Architecture anchor:** UPCC Master v1.3 + Curriculum Production System v1.3  
**Purpose:** ให้สถาบันอิสระสามารถออกแบบหลักสูตรที่กระชับ แต่ trace ได้ตั้งแต่ “ปัญหาจริง” จนถึง “สิ่งที่กลับมาอยู่กับผู้เรียน”

# A. เอกสารนี้ต้องตอบอะไรให้ครบ

เอกสารออกแบบหลักสูตรหนึ่งฉบับควรทำให้ผู้อ่านตอบได้ว่า:

```text
1. ปัญหาหรือการเปลี่ยนแปลงใดทำให้ต้องมีหลักสูตรนี้?
2. ผู้เรียนเข้ามาพร้อมประสบการณ์และข้อจำกัดอะไร?
3. ผู้เรียนกำลังใช้คำหรือกรอบใดมองปัญหาอยู่?
4. คำ/เลนส์ใหม่ใดจะทำให้เขาถามคำถามใหม่?
5. คำถามใหม่เปิด route / domain / tool / workflow อะไร?
6. ผู้เรียนต้องเรียน “ภาษาในการปฏิบัติ” อะไรบ้าง?
7. ต้องลงมือทำอะไร ไม่ใช่เพียงรู้อะไร?
8. จะฝึก ตรวจ แก้ และลดความช่วยเหลืออย่างไร?
9. หลังจบ อะไรกลับมาอยู่กับผู้เรียนจริง?
10. ผู้เรียนจะรู้ได้อย่างไรว่าอะไรทำเองได้ อะไรต้องตรวจ และอะไรต้องส่งต่อ?
11. ความรู้ที่ได้จะถูกเก็บเป็นทุนสำหรับปัญหาครั้งต่อไปอย่างไร?
```

แกนกลาง:

```text
LIVE PROBLEM
→ EXPERIENTIAL CAPITAL
→ CURRENT PREMISE / CURRENT WORDS
→ NEW WORKING WORDS
→ CHANGED QUESTIONS
→ ROUTES
→ OPERATIONAL LANGUAGE
→ TOOL / WORKFLOW / CRITERIA / ROLE
→ PRACTICE
→ CHALLENGE / VERIFY
→ REDUCE DECISIVE SUPPORT
→ HUMAN RETURN
→ TRANSFER / WORLD FEEDBACK
→ RETAINED KNOWLEDGE
→ NEXT PROBLEM
```

```text
ภาษา:

ผู้สอน / ผู้เชี่ยวชาญ:
เวอร์ชัน:
```

เขียนเพียง 1–2 ประโยค:

> หลักสูตรนี้ช่วยให้ผู้เรียน...

```text
หลักสูตรนี้ "ไม่ได้" อ้างว่า...
```

# 2. LIVE PROBLEM & PURPOSE — ปัญหาจริงและเหตุผลของหลักสูตร

นี่คือจุดเริ่ม ไม่ใช่ “หัวข้อที่อยากสอน”

## 2.1 Live Problem

```text
ปัญหา / สถานการณ์จริงคืออะไร?

เกิดกับใคร?

เกิดในบริบทใด?

ผลที่เกิดขึ้นคืออะไร?

เหตุใดวิธีเดิมยังไม่พอ?
```


```text

```

# 3. LEARNER CONTEXT & EXPERIENTIAL CAPITAL — ผู้เรียนไม่ได้เริ่มจากศูนย์

```text
accessibility:
```

## 3.2 Experiential Capital

บันทึกสิ่งที่ผู้เรียนได้เรียนรู้จากการ “อยู่กับปัญหา” มาก่อน:

```text
สิ่งที่เคยเห็น:
สิ่งที่เคยลอง:
สิ่งที่เคยล้มเหลว:
สิ่งที่เคยได้ผลบางส่วน:
ความแตกต่างที่ผู้เรียนสังเกตได้:
ผลกระทบที่เคยเกิดขึ้น:
```

## 3.3 Context Injection

ก่อนเรียน ผู้เรียนควรสามารถให้ข้อมูลเท่าที่เกี่ยวข้องว่า:

```text
เกิดอะไรขึ้น?

ผลที่จะเกิดถ้าพลาดคืออะไร?
อะไรยังไม่รู้?
```

# 4. CURRENT PREMISE & WORKING WORDS — ตอนนี้ผู้เรียนกำลังมองปัญหาด้วยคำอะไร

นี่คือส่วนที่ทำให้หลักสูตรของเราไม่กลายเป็น “content dump”

## 4.1 Current Premise

```text
ผู้เรียนกำลังเชื่อ / สมมติอะไรอยู่?

สมมติฐานใดอาจถูกต้อง?

สมมติฐานใดต้องตรวจ?

ข้อเท็จจริงใดห้ามหายเมื่อเปลี่ยนกรอบ?
```

## 4.2 Current Words

```text
คำที่ผู้เรียนใช้เรียกปัญหาปัจจุบัน:
คำที่ทำให้คำถามแคบเกินไป:
คำที่คลุมเครือ:
คำที่มาจากวัฒนธรรม / องค์กร / วิชาชีพ:
```

## 4.3 Working Words / Additional Lenses

สำหรับคำหรือเลนส์ใหม่แต่ละคำ:

```text
TERM:
ทำให้เห็นอะไรเพิ่ม?
เปิดคำถามอะไร?
เปิด domain / practice system ใด?
ข้อเท็จจริงใดต้องรักษาไว้?
ความเสี่ยงของคำนี้คืออะไร?
```

หลักการ:

```text
เปลี่ยนคำ
≠
เปลี่ยนความจริง

เป้าหมายคือ
add a lens
ไม่ใช่
delete reality
```

# 7. OPERATIONAL LANGUAGE — คำที่ทำให้ “เข้าไปทำงานได้”

คำศัพท์ไม่ใช่ภาคผนวก แต่เป็นประตูเข้าสู่ practice system

ต้องพิจารณา 6 กลุ่ม:

## 7.1 Problem-Junction Terms

```text
คำที่ทำให้เห็นปัญหา / ทางแยกใหม่
```

## 7.2 Tool Terms

```text
คำที่ต้องรู้เพื่อเลือกและใช้เครื่องมือ
```

## 7.3 Workflow Terms

```text
ขั้นตอน
dependency
branch
handoff
review point
completion condition
```

## 7.4 Criteria / Evidence / Failure Terms

```text
อะไรถือว่าดี?

ตรวจอย่างไร?
failure mode คืออะไร?
```

## 7.5 Skill / Role Terms

```text
ใครต้องทำอะไร?
ทักษะอะไร?
ผู้เชี่ยวชาญประเภทใด?
```

## 7.6 Boundary / Permission / Referral Terms

```text
อะไรเกินขอบเขต?
ใครมีสิทธิ์อนุมัติ?
เมื่อไรต้องส่งต่อ?
```

กฎ:

```text
จำคำได้
≠
ใช้คำเพื่อทำ next valid move ได้
```

# 8. CONTENT ARCHITECTURE — เนื้อหาใดควรอยู่ในหลักสูตร

แบ่งเป็น:

```text
MUST KNOW
จำเป็นต่อ capability

MUST DO
ต้องลงมือจริง

MUST CHECK
สิ่งที่ผู้เรียนต้องตรวจ / แยก / challenge

GOOD TO KNOW
มีประโยชน์ แต่ไม่จำเป็นต่อ core

DEFER
เก็บไว้สำหรับ next learning

DO NOT TEACH NOW
เนื้อหาที่น่าสนใจแต่เพิ่มภาระโดยไม่ช่วย route ปัจจุบัน
```

หลักการ:

> cheap knowledge ต้องยังคง problem-centered

ข้อมูลที่ไม่ช่วยปัญหา / route ควรถูกพัก ไม่ใช่สะสมเพราะ AI สร้างได้ง่าย

```text
[ ] มี actual practice หาก outcome คือ skill

[ ] retained knowledge ถูกทำให้ explicit

[ ] learner รู้ boundary / referral

[ ] closure จบให้ครบและไม่ตามเกินจำเป็น

[ ] claim ของหลักสูตรไม่แรงกว่า evidence
```

# 24. ตัวอย่างย่อ — หลักสูตร “AI เพื่อแก้ปัญหางานอย่างตรวจสอบได้”

## Live Problem

```text
คนใช้ AI สร้างคำตอบได้เร็ว
แต่ไม่รู้ว่าคำตอบไหนควรเชื่อ
และไม่รู้ว่าเมื่อไรต้องออกจากบทสนทนา AI ไปตรวจโลกจริง
```

## Experiential Capital

```text
เคยใช้ ChatGPT
เคยได้คำตอบที่ดูดี
เคยพบข้อมูลผิดภายหลัง
เคยค้น source แต่ไม่แน่ใจว่า source รองรับ claim หรือไม่
```

## Current Words

```text
"ถาม AI ให้เก่ง"
"prompt ดี"
```

## Working Words

```text
verification
claim

independent check
```

## Changed Question

จาก:

> ทำ prompt อย่างไรให้ได้คำตอบดีที่สุด?

เป็น:

> claim ไหนมีผลต่อการตัดสินใจ และควรตรวจด้วยวิธีที่เป็นอิสระอย่างไร?

## Route

```text
verification
→ evidence evaluation
→ source / data / calculation / expert
→ verification workflow
→ claim-match criteria
→ analyst / reviewer skill
```

## Operational Language

```text
claim

assumption

```

## Must Do

```text
สร้าง candidate route

ตรวจ source
เปรียบเทียบ claim กับ evidence
แก้คำตอบ
ทำ changed-case โดยลด AI
```

## Human Return

ให้โจทย์ใหม่ ผู้เรียนยังสามารถ:

```text

select verification route
check

refer if high-stakes
```

## Retained Knowledge

```text

source existence ≠ source support
high-stakes question อาจต้องใช้ expert
```

นี่แสดงความต่างระหว่าง “หลักสูตรสอน AI” แบบทั่วไป กับหลักสูตรที่ออกแบบจากแกน UPCC
